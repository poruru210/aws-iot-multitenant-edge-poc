# Web操作を中心とした登録・送信フロー（改訂案）

## 状態と位置付け

ユーザーの指摘を受け、CLI中心の初期仮定を見直した要件・設計案。Goデバイス、CDK v2 TypeScript、Trusted User方式、ThingTypeName=tenantId、S3直接Multipartは維持する。

**この文書は目標仕様であり、Web UI・常駐サービスの実装完了を示すものではない。** 現状のCLIは技術検証・保守診断用として残す。本書と旧文書の「Web画面・常駐サービスは対象外」が矛盾する場合、今後のUX要件については本書を優先する。

確認した現行コード:

- `cmd/edge/main.go` の `upload` は `device.Clients` で作ったS3クライアントを直接使用する。先に `credentials` を実行する必要はない。
- `internal/device/credentials.go` はIoT Credentials Providerを `aws.CredentialsCache` で包む。初回利用時に取得し、更新が必要な時の利用で再取得する。現行設定は期限の約96〜120秒前から更新対象にする。アイドル時の定期更新ジョブではない。
- 現行の `init` / `claim` / `provision` にはファイル受け渡しがある。ここはWeb化だけでなく、処理を連続実行する仕組みへの変更が必要。
- 現行 `issue-claim.ts` は `AWS_IAM` と `requestContext.identity.userArn` を前提とする。JWTログイン画面を付けるだけでは認証・テナント認可を置き換えられない。

## 1. UXの原則

通常利用者に要求するのは、対象デバイスと登録先顧客の確認、必要な送信設定、結果の確認だけとする。CSR、Claim、Role Alias、STS、IAM、S3 Multipartの各操作を独立した画面やボタンとして公開しない。

サービスマンはAWS CLI、AWSプロファイル、アクセスキーを扱わない。AWS環境のデプロイや保守は開発・管理担当の別作業とする。

Web画面は操作・状態確認を担当し、登録・認証・転送はGoエージェントが担当する。ブラウザの画面遷移・終了・作業者のログアウトで、開始済みの登録や送信ジョブを中断させない。

## 2. 画面の配置と責務（提案）

| 配置 | 主な役割 |
|---|---|
| エッジの設定Web画面 | 対象デバイスの確認、接続準備、登録開始、エッジ内の送信対象・送信履歴・障害の表示 |
| クラウドの登録画面 | 作業者ログイン、権限のある顧客の選択、対象デバイスとの照合、登録承認 |
| Goエージェント | 鍵・CSR、Claim受領、MQTT登録、認証情報管理、送信キュー、S3直接転送、状態永続化 |
| 登録バックエンド | 作業者とテナントの認可、登録セッション、Claim発行、台帳、登録前フック |

既存エッジに設定Web画面があるなら、そこへ統合することを優先する。独立PoCではGoのHTTPサーバーに設定画面を組み込む案とする。クラウド画面を開く部分も登録ウィザードの一部として案内する。

クラウドから工場LANへの直接接続や、クラウドページのJavaScriptがLAN上の端末へ無条件にアクセスできることを前提にしない。登録情報の受け渡しはエッジ発のHTTPS通信で成立させる。ローカル画面は認証、CSRF対策、Host/Origin検証を行う。LAN公開する場合はTLSの信頼設定も必要であり、認証なしのHTTPを全インターフェースへ公開しない。

## 3. 初回登録の利用者フロー

| 手順 | 利用者に見せるもの・操作 | 裏側で行うこと |
|---|---|---|
| 1. 対象の確認 | エッジの設定画面を開き、機器名・製造番号・現在の登録状態を確認 | 既存登録とローカル状態を検査。登録済みなら新規登録へ誘導しない |
| 2. 接続準備 | 接続診断の結果を表示。必要な場合だけネットワーク設定 | DNS、時計、TLS、登録先への到達性を確認。Claimはまだ発行しない |
| 3. 登録開始 | 「クラウドに登録」を押す | エッジ内で本番鍵・CSRを準備。公開鍵に結び付いた短期登録セッションを開始 |
| 4. 顧客の選択 | クラウド登録画面へ移動してログイン。許可された顧客名を一覧から選ぶ | 作業者を認証し、サーバー側で所属・登録権限を検証 |
| 5. 最終確認 | 「顧客Aに機器Xを登録します」を確認して実行 | 対象機器と登録セッションを照合し、tenantId・deviceId・公開鍵を固定 |
| 6. 自動登録 | 「登録中」を表示。ファイルのダウンロード・コピーは要求しない | GoがClaimを自動受領し、MQTT/TLSでCSR提出・RegisterThing。フックで所属を強制 |
| 7. 利用確認 | 「接続を確認しています」を表示 | 本番証明書を安全に保存し、取得した認証情報で自分の領域へ小さな試験データを送信 |
| 8. 完了 | 顧客名、機器名、登録完了、送信テスト結果を表示 | 台帳と端末状態を照合して利用可能にする。短期Claimを破棄 |

登録完了と送信可能は分ける。証明書の登録が成功してもS3へ到達できない場合は「登録済み・送信確認待ち」であり、完了と偽って表示したり、再登録で解消しようとしたりしない。

### 入力させない情報

tenantIdやThing名はサーバー・エージェント側で確定する。顧客名と不変の内部IDは分離し、顧客名の変更でS3パスを変更しない。製造番号等は機器確認に利用するが、自己申告の番号だけで正当な機器と判断しない。接続先、Role Alias、バケット、S3のテナントプレフィックスは通常画面で編集させない。

### 登録画面と端末を結ぶ方法

提案は、短期の登録セッションを使った承認方式。機器画面に表示した確認コードやリンクからクラウド側で同じ機器を確認する。確認コードは補助手段であり、単独ではClaim取得権限にしない。

未登録の端末が使うセッション開始APIは、登録・S3権限を与えない。受付制限、短期失効、試行回数制限を設け、公開鍵と署名済みチャレンジで端末側の鍵保持を確認する。作業者承認後のClaim受け取りにも同じ鍵との結び付けとリプレイ防止を要求する。これはアプリ独自の登録承認セッションであり、CognitoがOAuth Device Authorization Grantを提供すると仮定する設計ではない。

エッジがオンラインで登録可能になってから、登録APIが `CreateProvisioningClaim` を呼ぶ。Claimの短期秘密鍵はエッジへの保護された応答にだけ含め、ブラウザへの表示、ダウンロード、台帳の平文保存、ログへの出力をしない。本番用秘密鍵は最初から最後までエッジ内に保持する。

5分のClaim期限に作業者の顧客選択時間を含めない。通信失敗時の再試行では既存のClaim・証明書・台帳状態を照合し、別の登録を無制限に作らない。承認の期限が切れた場合は、必要なところだけ再確認を求める。

## 4. 通常のアップロードフロー

本来の入力は、工場の既存収集処理がエッジに集めたデータである。作業者PCのブラウザからファイルを毎回選び直す運用にはしない。

定常運用の入口は、既存の収集処理が確定したファイルをGoエージェントの送信キューに渡すことを基本案とする。独立PoCでは、許可されたエッジ上の保存領域のファイル一覧から「送信」できる手動試験も用意する。ブラウザPC側のファイル選択を、エッジ内のファイル選択と混同しない。

```text
収集済みの確定ファイル
  → 送信ジョブを永続化
  → エージェントがジョブを開始
  → S3のAPI呼び出しで必要な認証情報を自動取得
       キャッシュが有効なら再利用
       未取得・更新時期なら証明書でCredentials Providerへ取得要求
  → GoからS3へ直接Multipart Upload
  → 結果と再開用情報を保存
  → 画面へ進捗・完了を反映
```

「STS取得」ボタンや送信前の認証コマンドは設けない。ファイルごと・パートごとに必ずSTSを新規取得する設計にもしない。常駐サービス内でCredentialsCache/S3クライアントを適切に共有し、送信要求がない間はSTS更新だけのために定期通信しない。

デバイス証明書と秘密鍵は保護された端末ストレージへ保存する。一時認証情報は原則プロセスメモリで扱い、画面、ブラウザストレージ、設定ファイルへ渡さない。サービスマンのWebログインが切れても、登録済みデバイスの通常送信は継続する。

### 再試行・再開

ネットワーク切断や一時的なサービス障害は、上限と間隔を設けた再試行・送信キュー待機で処理する。証明書失効、所属不整合、AccessDenied等は無制限再試行せず「対応が必要」とする。認証に失敗しても管理者のAWS認証情報へフォールバックしない。

UploadId、ファイル識別子、パート情報、送信状態は永続化する。画面を閉じても送信を続け、プロセス再起動後は状態を照合して再開する。利用者にstateファイル名やロックファイルの削除を要求しない。別のジョブ・プロセスが動作中かを確認せずにロック解除しない。

CompleteMultipartUploadの応答が不明な場合は、成功とも失敗とも即断しない。「結果確認中」として保留し、管理バックエンドの照合等で保存先と整合性を確認する。これを実現する仕組みは現行CLIには未実装であり、実装時に追加する。自動再送で同じオブジェクトを安易に上書きしない。

## 5. 最小限の画面

| 画面 | 表示・操作 |
|---|---|
| 登録ウィザード | 機器確認、接続準備、作業者ログイン、顧客選択、登録確認、進捗、試験結果 |
| デバイス概要 | 登録先、機器名、直近の接続・送信状態、未送信件数、使用容量 |
| 送信一覧 | エッジ上の対象ファイル、待機/送信中/通信待ち/完了/対応必要、進捗、再試行・保留 |
| 接続診断・詳細 | 原因の切り分け、問い合わせ用ID、権限のある担当者向け診断。秘密情報は出さない |

未送信件数や「接続良好」には取得時刻を表示する。単に最後の成功が古いだけで、現在の接続状態が良好であると断定しない。

失敗時は「エラー」だけではなく、次に何をすべきかを示す。例: 「通信が戻ると自動再開します」「登録先を確認してください」「証明書の確認が必要です」。AWSのエラーコードは詳細表示へ分ける。

## 6. 実装変更の範囲

| 対象 | 再利用・変更内容 |
|---|---|
| `internal/device/credentials.go` | 既存の遅延取得・期限前更新を再利用。常駐サービス単位でキャッシュを共有し、更新・並列呼び出し試験を拡充 |
| `internal/device/provision.go` / `config.go` | ファイル受け渡し前提のCLI処理から、Webと登録セッションで呼べるGoサービス層へ分離 |
| `internal/device/upload.go` | 転送処理を再利用し、永続ジョブ、状態通知、ブラウザに依存しないライフサイクルを追加 |
| `cmd/edge` | 開発・診断用に維持。通常利用者向けには常駐サービス起動とWeb操作を用意 |
| Web UI | 既存エッジ画面を優先して統合。独立PoCではGo配信のUIとクラウド登録画面を追加 |
| 登録API | 人のWeb認証と、未登録端末の短期登録セッションを分離。作業者の顧客別認可を明示的に実装 |
| CDK | Web配信、必要な認証基盤、登録セッションAPI・台帳を追加。既存のIoT/S3制約は維持 |
| 試験 | 技術試験に加え、Webだけで登録・送信、期限切れ、画面終了、再起動、権限改ざんを検証 |

Web認証は既存の業務IdPがあれば優先する。独立PoCでの候補はCognito User Poolのブラウザログイン。公開クライアントならAuthorization Code + PKCEを使う。選定したAPI Gateway方式に対応するAuthorizerで検証し、JWTの正当性と業務上のtenant権限を別々に評価する。

**従来のテナント別 `execute-api:Invoke` IAM権限を、JWTを付けただけで維持できるとは扱わない。** ブラウザ用経路ではサーバー側の作業者・テナント対応で認可する。端末のS3用IAMポリシーは従来どおりThingTypeName/ThingNameに限定する。

フロントエンド追加のために、転送データをAPI Gateway/Lambdaや作業者PCへ迂回させない。S3のデータ経路はエッジからの直接送信を維持する。

## 7. UX受入条件（今後の試験）

1. サービスマンはターミナル、AWSアクセスキー、証明書ファイル操作なしで登録できる。
2. 許可された顧客だけが選択でき、HTTP要求を改ざんしても他顧客へ登録できない。
3. 別端末の登録セッション・公開鍵への差し替え、期限切れコード、再利用を拒否する。
4. ログイン・顧客選択に時間がかかっても、未発行のClaim期限を消費しない。
5. 二重クリック・画面再読込でThingや証明書を重複作成しない。登録済み機器を勝手に初期化しない。
6. 登録完了とS3送信確認の結果を区別し、途中失敗から必要な工程だけ復旧できる。
7. credentialsコマンド未実行でも、通常の送信から認証情報を取得できる。
8. 連続・並列送信は有効な認証情報を再利用し、期限をまたいでも必要時に更新する。更新失敗時に別の認証情報へフォールバックしない。
9. アイドル時に認証情報を無意味に取得し続けない。
10. 作業者PCではなくエッジ上の許可されたファイルを送信する。任意のパスや秘密鍵ファイルは選択できない。
11. ブラウザ終了・作業者ログアウト後も開始済み送信が継続する。新しい操作には必要な認可を要求する。
12. 通信断・エージェント再起動後の再開に、利用者によるcheckpoint/lockファイル操作を必要としない。
13. 完了応答を失っても無条件に「完了」とせず、確認状態で二重送信を防ぐ。
14. 証明書失効・AccessDeniedは適切な対応案内となり、無限再試行しない。
15. ブラウザ、APIログ、診断画面に本番秘密鍵・Claim秘密鍵・STS秘密情報が漏れない。
16. 登録先テナント・デバイス以外のS3領域への書き込み拒否を、正常系と組み合わせて確認する。

現行の技術CI成功を、このWeb UX受入条件の成功とは数えない。

## 8. 未確認の統合条件

既存エッジのWeb画面・ログイン基盤の有無、既存収集処理が送信対象を引き渡す方法、常駐サービスを配布するOSはまだ確認していない。これらは追加サービスの重複を避けるための統合条件であり、コマンド主体へ戻す理由にはしない。

現段階の提案は「既存画面を優先」「既存IdPを優先」「確定ファイルの送信キュー連携」。GoとCDK v2 TypeScriptという指定は変更しない。クラウド全体監視、全顧客向け管理ポータル、既存マシンの収集アダプター、TPM、証明書自動ローテーション、テナント移管、実AWSデプロイは別途の範囲として扱う。
